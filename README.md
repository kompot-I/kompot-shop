# BRICKBOX (Vite + Vue 3)

Витрина Lego-минифигурок. Та же логика и дизайн, что были в vanilla-версии,
но теперь разложены по компонентам — так проще расширять и тестировать.

## Запуск

```bash
npm install
npm run dev
```

Откроется на `http://localhost:5173` с hot-reload — любое изменение в `.vue`
файле применяется мгновенно, без перезагрузки страницы.

Другие команды:

```bash
npm run build       # продакшн-сборка в dist/
npm run preview     # локально посмотреть на собранный dist/
npm run test         # прогнать тесты один раз
npm run test:watch  # тесты в watch-режиме, полезно во время разработки
```

В IntelliJ IDEA просто открываете папку проекта и запускаете `npm run dev`
через встроенный терминал — никакого отдельного плагина не нужно.

## Структура и почему именно так

```
src/
├── main.js                     точка входа: создаёт приложение, подключает базовые стили
├── App.vue                     корневой компонент — только сборка кусков вместе
│
├── api/
│   └── products.js             весь fetch-код в одном месте
│
├── composables/                реактивная ЛОГИКА без единого тега разметки
│   ├── useProducts.js          загрузка каталога + isLoading/error
│   └── useProductFilters.js    поиск / фильтр / сортировка
│
├── components/                 UI: шаблон + логика + стили одним файлом
│   ├── TheHeader.vue
│   ├── FilterChips.vue
│   ├── ProductCard.vue
│   ├── ProductGrid.vue
│   ├── EmptyState.vue
│   └── icons/
│       ├── BrickIcon.vue
│       └── SearchIcon.vue
│
├── constants/conditions.js     единый источник правды: состояния товара
├── utils/format.js             мелкие чистые функции (форматирование цены)
│
└── styles/
    ├── tokens.css               переменные темы (:root) — меняете дизайн здесь
    └── base.css                 reset и общие правила, не привязанные к компоненту
```

### Компонент vs composable — в чём разница

Это главное разделение в приложении, и стоит его понимать осознанно:

- **Компонент** (`.vue` файл) — это то, что рисуется на экране. У него есть
  шаблон, и обычно — стили. Пример: `ProductCard.vue` знает, как выглядит
  карточка товара.
- **Composable** (`use*.js` файл) — это переиспользуемый кусок реактивной
  логики без единого тега разметки. `useProductFilters.js` ничего не знает
  о том, как что-то отрисовать — он просто хранит `search`/`condition`/`sort`
  и отдаёт отфильтрованный список. Поэтому его можно протестировать без
  рендеринга UI вообще (см. `composables/__tests__/`) — и в теории использовать
  повторно, например, если появится вторая страница со своим списком товаров.

Грубая аналогия на ваш бэкграунд: composable — это примерно как сервис
в Spring (несёт логику, не знает о представлении), компонент — как
контроллер + view вместе.

### Тесты

Лежат рядом с кодом в папках `__tests__/` — это конвенция JS/TS-экосистемы,
отдельного дерева `src/test/...` как в Java здесь не будет. Стек — **Vitest**
(тот же движок, что у Vite, поэтому конфиг общий) + **@vue/test-utils** для
монтирования компонентов в виртуальном DOM (jsdom).

Два файла-примера показывают оба вида тестов:
- `useProductFilters.spec.js` — тест чистой логики, компонент не участвует.
- `ProductCard.spec.js` — монтирует реальный компонент и проверяет то, что
  увидел бы пользователь: текст на экране, disabled-кнопку, клик.

## Формат товара (public/products.json)

Не изменился:

```json
{
  "id": "уникальный-id",
  "name": "Название",
  "category": "Star Wars",
  "description": "Короткое описание",
  "price": 1200,
  "currency": "RUB",
  "quantity": 1,
  "condition": "new | like_new | used",
  "image": "https://... или пусто (будет плейсхолдер)",
  "buyLink": "куда ведёт кнопка «Купить»"
}
```

Своё фото — либо ссылка, либо файл в `public/images/...`, путь вида
`/images/sw-001.jpg`.

## Дальше — бэкенд на Kotlin

`src/api/products.js` сейчас делает `fetch("/products.json")`. Когда поднимете
Spring Boot с эндпоинтом `GET /api/products`, отдающим тот же формат
(`{ "products": [...] }`), меняете в этом файле только URL. Ни composables,
ни компоненты трогать не придётся — они работают с массивом объектов, а не
с тем, откуда он взялся.

## Дальше — Telegram Mini App

Тот же принцип, что и раньше: добавляете `telegram-web-app.js` в `index.html`
и инициализируете SDK в `main.js` (`Telegram.WebApp.ready()`), сама вёрстка
и логика переносятся без переписывания.
